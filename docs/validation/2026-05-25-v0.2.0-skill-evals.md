# v0.2.0 Skill Eval Summary

## Scope

This validation pass covers the `v0.2.0` workflow-skill improvements applied to:
- `skills/incu-way-development/SKILL.md`
- `skills/incu-way-bugs/SKILL.md`
- `skills/snyk-remediation/SKILL.md`

The focus of the release was:
- stronger triggering and discoverability
- stronger early discovery and intake behavior
- better anti-guessing discipline before PRDs, fix plans, or remediation plans

## Eval approach

Two rounds of eval-style checks were run.

### Iteration 1 — First-response behavior

Goal: verify that the revised skills change the assistant's first move in ambiguous workflows.

Evaluated scenarios:
- ambiguous client feature request
- incomplete production bug report
- vague Snyk remediation request

Result summary:
- `with_skill` average pass rate: `1.0`
- `without_skill` average pass rate: `0.5`
- delta: `+0.50`

Key takeaways:
- the revised skills consistently produced stronger intake behavior
- the strongest gain was in ambiguous early workflow behavior
- the baseline often asked some good questions, but still skipped codebase discovery or drifted into assumptions too early

### Iteration 2 — Deeper workflow artifacts

Goal: verify that the revised skills can carry a realistic scenario to the correct next artifact and stop at the correct gate.

Evaluated scenarios:
- discovery -> PRD gate
- intake -> analysis/fix-plan gate
- intake/scan context -> findings/plan gate

Result summary:
- `with_skill` average pass rate: `1.0`
- `without_skill` average pass rate: `0.75`
- delta: `+0.25`

Key takeaways:
- `incu-way-development` remained clearly better in the deeper eval
- `snyk-remediation` still showed useful improvement in intake/context rigor and scoping discipline
- `incu-way-bugs` was less discriminating in this round because a strong baseline could also produce decent staged artifacts once the scenario was well structured

## Interpretation

This is a good `v0.2.0` release.

The edits clearly improved the behavior the release targeted. The clearest measurable benefit is earlier in the workflow:
- when the request is ambiguous
- when the assistant is tempted to guess scope or intent
- when the right behavior is to stop and clarify before turning uncertainty into a plan

The deeper evals also show an important limitation: once a scenario is already well staged, a competent baseline model can sometimes approximate the workflow even without the skill. That means future eval work should not only test artifact production, but also test whether the skill causes uniquely better judgment under realistic ambiguity.

## Recommended next step

Treat this release as `v0.2.0` and move forward.

For the next iteration, the highest-value follow-up is:
- improve the bug eval so it better isolates the unique value of `incu-way-bugs`

Possible `v0.3.0` directions:
- sharpen `incu-way-bugs` further around evidence discipline and canonical fix-plan gating
- add trigger-eval coverage for all three skill descriptions
- add one repo-specific real-world eval in a target application instead of a pure simulated workflow
